# Armina Hair — исходная версия Telegram Mini App

Исходный код демонстрационного MVP (для реального использования требуется настройка хостинга и проверка интеграций): **FastAPI + SQLAlchemy/aiosqlite + Vanilla JS + Telegram WebApp SDK**.
Есть каталог услуг, выбор мастера, календарь и свободные слоты, бронирование с блокировкой пересекающихся интервалов, Telegram-уведомления, модерация записи администратором.

Подготовлено для **@ArminaHair_Bot** и репозитория **lordiklolkek/Armina-hair-tma**. В корне есть `render.yaml` для демозапуска на Render Free и `.python-version` с Python 3.12. Быстрые инструкции: [LAUNCH.md](LAUNCH.md). Выполненные проверки: [VALIDATION.md](VALIDATION.md).

## 1. Запуск локально

Нужен Python **3.11+**.

```bash
cd armina-hair-tma
python -m venv .venv
# Windows PowerShell:
.venv\Scripts\Activate.ps1
# macOS/Linux:
# source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env      # Windows: Copy-Item .env.example .env
uvicorn main:app --reload
```

Откройте в браузере `http://127.0.0.1:8000`. Просматривать услуги и слоты можно без Telegram. **Создать запись в обычном браузере нельзя**: сервер требует подписанное `Telegram.WebApp.initData`. Проверять оформление заказа нужно внутри Telegram.

API-документация: `http://127.0.0.1:8000/docs`, проверка работы: `/health`. База создаётся автоматически, вместе с тестовыми услугами и мастерами, при первом старте. Демо-данные вымышлены. Изменяйте начальные данные в `database.py` **до первого старта**; после первого старта каталог живёт в `salon.db` и не перезаписывается.

## 2. Создайте Telegram-бота

1. Откройте **@BotFather**, используйте `/newbot` и получите токен.
2. В `.env` укажите `BOT_TOKEN=...` и `BOT_USERNAME=ArminaHair_Bot`. Сервер проверит через `getMe`, что токен принадлежит нужному боту, **до изменения его настроек**.
3. Укажите `ADMIN_CHAT_ID`: числовой ID личного чата с админом или ID группы с ботом (`-100...`). Для личного ID админ должен первым отправить `/start` боту. Для группы бот должен быть участником; для корректной проверки полномочий сделайте его администратором группы. Альтернатива — задайте конкретные Telegram ID в `ADMIN_USER_IDS`.
4. Заполните `SALON_NAME` и **реальный** `SALON_ADDRESS`.
5. Создайте `WEBHOOK_SECRET` длиной не менее 32 символов (например, `python -c "import secrets; print(secrets.token_urlsafe(32))"`). Используйте только буквы, цифры, `_` и `-`.
6. После получения публичного HTTPS-адреса добавьте его в `PUBLIC_BASE_URL` без завершающего `/`. На Render адрес автоматически берётся из `RENDER_EXTERNAL_URL`, если `PUBLIC_BASE_URL` пуст: повторный деплой ради адреса не требуется. Используйте только HTTPS-адрес без пути, параметров и пароля.

При старте FastAPI автоматически вызывает Telegram **setWebhook** с `secret_token`, **setChatMenuButton** и **setMyCommands**, привязывая приложение к кнопке меню бота. Команда `/id` в личном чате выдаёт пользователю его числовой Telegram ID. Когда клиент напишет боту `/start`, он также получит кнопку «Открыть запись». Для красивой кнопки запуска на странице бота откройте @BotFather → Bot Settings → Configure Mini App (Main Mini App), укажите тот же HTTPS URL. После этого доступна прямая ссылка `https://t.me/ArminaHair_Bot?startapp`.

Telegram требует публичный **HTTPS**. Для локальной проверки внутри Telegram можно поднять HTTPS-туннель (например, Cloudflare Tunnel или ngrok) на порт 8000, указать его URL в `PUBLIC_BASE_URL` и перезапустить сервер. Адрес туннеля должен оставаться действующим.

**Важно:** бот обычно не может первым отправить сообщение клиенту, пока тот не открыл личный чат бота и не нажал `/start`. Для получения уведомлений попросите пользователя сначала запустить бота.

## 3. Как работает запись

- `GET /api/services` — опубликованные услуги с мастерами.
- `GET /api/slots?service_id=1&date=2026-10-12&master_id=1` — свободные слоты (`master_id` необязателен, тогда подходит любой мастер).
- `POST /api/book` — создаёт заявку со статусом `pending`; обязателен заголовок `X-Telegram-Init-Data` из Telegram SDK.
- `POST /telegram/webhook` — получает обновления Telegram и кнопки модерации; защищён заголовком `X-Telegram-Bot-Api-Secret-Token`.

Временная зона **Asia/Yerevan**, рабочие интервалы хранятся в местном времени, а интервалы бронирования — в UTC. Доступны даты на 30 дней вперёд. Интервал каждого слота — 30 минут; минимальная запись за 60 минут до начала. Не допускаются пересекающиеся заявки со статусом `pending` или `confirmed`; `cancelled` освобождает время.

**Защита от двойного бронирования:** при `POST /api/book` сервер берёт SQLite-транзакцию `BEGIN IMMEDIATE` **до** чтения занятости и удерживает её до вставки заявки. Параллельные запросы к одному файлу БД сериализуются. Этот подход рассчитан на **одну общую SQLite БД на одном сервере**; не храните независимые SQLite-копии на разных инстансах.

После бронирования клиент получает сообщение «ожидает подтверждения», админ — уведомление с «Подтвердить / Отменить». Только авторизованный администратор может нажать кнопку. Решение изменяет статус заявки, освобождает слот при отмене и уведомляет клиента. **Если Telegram API недоступен, бронь сохраняется**, а сбой отправки пишется в лог — для серьёзного использования стоит добавить очередь повторных уведомлений.

## 4. Render: запуск на бесплатном тарифе **только для демонстрации**

Рекомендуемый путь: загрузить **содержимое** проекта в корень GitHub-репозитория, затем в Render выбрать **New → Blueprint**, подключить этот репозиторий и применить `render.yaml`. Он задаёт Python, команды сборки/запуска, один процесс сервера и `/health`. В защищённых настройках Render вводятся `BOT_TOKEN` и числовой `ADMIN_CHAT_ID`; в GitHub эти значения не добавляются. `WEBHOOK_SECRET_SEED` генерируется самим Render, а приложение преобразует его в разрешённый Telegram секрет. Настройки применяются при настоящем запуске сервера, архив сам по себе бота не подключает.

При ручном создании Web Service:

1. Создайте GitHub-репозиторий (добавьте все файлы проекта, кроме `.env`, `.db`, `.venv`).
2. В [Render](https://render.com/) выберите **New → Web Service → Connect Repository**.
3. Runtime — Python, Build Command: `pip install -r requirements.txt`.
4. Start Command: `uvicorn main:app --host 0.0.0.0 --port $PORT`.
5. План `Free` (если доступен), Environment: `BOT_TOKEN`, `ADMIN_CHAT_ID`, `WEBHOOK_SECRET`, `SALON_NAME`, `SALON_ADDRESS`, `DATABASE_URL`.
6. На Render приложение само получит адрес `https://имя.onrender.com`. `PUBLIC_BASE_URL` нужен только для переопределения адреса, например при использовании собственного домена. Проверьте `/health`, `/docs` и кнопку бота.

⚠️ **Render Free не подходит для реального салона с локальным SQLite:** файловая система эфемерная — `salon.db` **теряется при засыпании, рестарте или передеплое**. К тому же бесплатный сервис засыпает после простоя и может долго просыпаться. Не принимайте записи реальных клиентов с этой конфигурацией.

Для реального салона с этим кодом: выберите VPS или платный Render с persistent disk и укажите расположение SQLite-файла на сохраняемом диске, например `DATABASE_URL=sqlite+aiosqlite:////var/data/salon.db`. Делайте резервные копии БД, задайте мониторинг, продумайте хранение персональных данных и ограничение частоты запросов. Для масштабирования на несколько серверов нужна PostgreSQL и транзакционная блокировка на уровне PostgreSQL (текущий код заточен под SQLite).

## 5. Vercel

**Не разворачивайте данный SQLite-проект на Vercel как сервис реальных записей.** Vercel использует эфемерное хранилище для функций: постоянный SQLite-файл на нём не поддерживается. На Vercel можно разместить только *отдельную статическую часть* после настройки внешнего backend и CORS, либо перейти на внешнюю БД и изменить бэкенд. Для исходного монолитного приложения проще VPS или Render с persistent disk.

## 6. Что адаптировать под настоящий салон

- `database.py` — услуги, цены, длительность, мастера, расписания; начальные данные добавляются только при пустой таблице услуг.
- `.env` — адрес салона, бот и администратор.
- `static/style.css` — визуальное оформление; `static/app.js` — клиентский сценарий.
- В версии 2 есть базовая админ-панель для записей, услуг, мастеров, графиков и выходных. Перенос клиентом, напоминания, оплата, мультисалонность и полноценная CRM ещё не реализованы.

## 7. Безопасность

- Сервер **не доверяет** `initDataUnsafe`: проверяет HMAC по `initData`, `auth_date` (24 часа), и использует только проверенный Telegram ID.
- Админские действия проверяют ID исходного чата и полномочия через `getChatMember` или разрешённые ID.
- Вебхук использует Telegram `secret_token`, а админские кнопки не позволяют повторно обработать решение.
- Все клиентские поля отображаются через HTML escaping в сообщениях бота; в браузере используется безопасный `textContent`.
- Не публикуйте `.env`, токен, контакты клиентов и `.db`. Настройте HTTPS, политики хранения/удаления персональных данных и защиту от злоупотреблений перед продажей клиентам.

Документация: [Telegram Mini Apps](https://core.telegram.org/bots/webapps), [Telegram Bot API](https://core.telegram.org/bots/api), [Render Free](https://render.com/docs/free), [Vercel SQLite](https://vercel.com/kb/guide/is-sqlite-supported-in-vercel).

## 8. Проверка тестами

```bash
python -m pip install pytest pytest-asyncio
pytest -q
node --test tests/frontend.test.cjs
```

Тесты используют временную SQLite-базу, генерируют корректно подписанные `initData`, проверяют параллельную запись, пересекающиеся интервалы, отмену, права администратора, атомарное сохранение графика, запуск FastAPI, вебхук, настройку бота и скрытие токена в ошибках. Тесты JavaScript проверяют обновление слотов и запоздалые ответы. Для автотестов Telegram API заменён заглушкой; **доставку реальных сообщений** нужно проверить отдельно со своим ботом.

## 9. Панель управления (версия 2)

В приложении появилась отдельная **административная панель** по адресу `https://ВАШ_ДОМЕН/admin`.

После настройки HTTPS и `ADMIN_CHAT_ID` отправьте боту **`/admin` в личном чате**. При наличии прав он выдаст кнопку «Панель управления». Для индивидуального владельца проще задать `ADMIN_CHAT_ID` равным **личному числовому Telegram ID** владельца, либо записать его ID в `ADMIN_USER_IDS` (через запятую, если владельцев несколько). **Username ботa не является числовым ID**. Доступ к административным API дополнительно проверяется на сервере по подписи `initData` и ID пользователя Telegram, поэтому знать URL недостаточно.

Администратор может:

- Просматривать заявки и подтверждать/отменять их, фильтровать по статусу или дате.
- Добавлять/редактировать услуги, цены, длительность и видимость каталога.
- Добавлять/редактировать мастеров, их навыки и доступность.
- Менять часы работы по дням недели и задавать **полные выходные дни**.

Внимание: новая БД или существующая БД обновляется новой таблицей `master_days_off` автоматически через `create_all`. Для прочих будущих изменений схемы нужны миграции. Изменение расписания **не отменяет старые заявки**, даже если они выпадают из нового графика — владельцу следует просмотреть записи перед изменениями. Интерфейс расписания предполагает один рабочий интервал в день; API технически может хранить несколько. Для полноценных правил перерывов и праздников в нескольких салонах понадобится развитие интерфейса.

### Демо-настройки

**Armina Hair**, Капан. Имена мастеров, цены, услуги и рабочие часы из `database.py` — вымышленные демонстрационные данные, **не факт о реальном салоне**. Адрес в `.env.example` — текст-заглушка. Перед запуском с реальными людьми укажите настоящий адрес и проверьте все параметры. Не публикуйте чужие телефоны или адреса.

### Ограничения, оставшиеся перед коммерческим запуском

1. Настроить сохраняемый диск и ежедневные резервные копии. Бесплатный эфемерный хостинг не подходит.
2. Добавить повторную доставку Telegram-уведомлений (в текущем коде при временном сбое Telegram состояние брони сохранится, но уведомление не будет повторено автоматически).
3. Внедрить миграции БД, управление доступами администраторов, экспорт/удаление персональных данных, политику хранения, rate limiting.
4. Добавить расписание с перерывами в UI, отдельные выходные мастеров и ограничения на ближайшие дни (уже есть базовые полные выходные).
5. Провести интеграционное тестирование реальными аккаунтами Telegram и нагрузочное тестирование перед использованием в салоне.
6. Эта версия односалонная: мультисалонность потребует отдельной сущности салона, разграничения БД/данных по `salon_id` и управления подключениями нескольких ботов. Никогда не выдавайте один общий `/admin` разным независимым салонам.
