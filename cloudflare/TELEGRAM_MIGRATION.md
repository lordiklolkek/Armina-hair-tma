## Одноразовый механизм и повторный выпуск

`src/cutover.ts` не имеет клиентского endpoint. Запускается только при наличии уникального TELEGRAM_CUTOVER_REQUEST в операторской конфигурации, после явного разрешения. Перед записью проверяет точный HTTPS origin новой версии, getMe, ожидаемый старый webhook и guard старого Render с точным RENDER_GUARD_COMMIT. Затем меняет webhook без сброса очереди, проверяет его, меняет и проверяет меню. Один request исполняется один раз; при неопределённом результате повторной записи нет. Секреты и тексты ошибок не сохраняются.

В постоянной конфигурации TELEGRAM_CUTOVER_REQUEST отсутствует. Не добавлять его в GitHub и не создавать новый request для обычного deploy. Наличие успешной строки cutover в integration_status — журнал операции, а не команда повторить её. После неудачи сначала проверить фактический getWebhookInfo и меню, затем определить требуемое действие и разрешение.

Монитор Cron вызывает только getMe/getWebhookInfo. Его безопасное состояние доступно администратору в «Настройки → Уведомления → Проверить подключение бота». Проверять свежесть checked_at; сохранённое старое успешное состояние не доказывает текущую доступность. Фоновые события могут появляться с задержкой при распространении расписания; не включать платный план ради неё.

## Возврат и сохранение старого сервиса

Для возврата подготовлены работающий Render с отключённой авторегистрацией, прежний webhook-ключ в закрытом хранилище и исходный адрес `https://armina-hair-tma-demo.onrender.com/telegram/webhook`. Не выводить ключ при диагностике. Возврат меняет действующий бот и требует отдельного согласования, кроме действий, уже явно разрешённых пользователем для конкретного инцидента.

Перед возвратом проверить Render health/guard, сохранить текущее безопасное состояние Telegram и D1 export вне GitHub. После setWebhook со старым ключом проверить точный адрес; не сбрасывать pending updates. Меню также проверять отдельно: успешная смена webhook не доказывает смену меню. Не включать автоматическую регистрацию в Render и не откатывать его к старому коду без guard. Не импортировать старую SQLite в новую D1 и не затирать новую базу. Старый сервис не удалять и не отключать до завершения согласованного периода проверки.

## Живые проверки — частично завершены

1. Владелец/уполномоченный администратор открывает приложение через новое меню и /start. Обычный клиент не видит управление. ADMIN_IDS хранится как закрытый серверный список; новому человеку доступ предоставляется только по разрешению.
2. **Выполнено:** пользователь отправил тест самому себе и подтвердил получение. D1 selftest=sent, attempts=1, last_error=null; три ответа на реальные входящие события также sent. Это ещё не уведомления о визитах/напоминания. Прямой путь: Управление → Уведомления. Другим людям без разрешения сообщения не отправлять.
3. **Основной сценарий выполнен на аккаунте владельца:** D1 подтвердил одно принятое приглашение, пользователь подтвердил кабинет мастера. Задержка ответа /start устранена отдельной немедленной отправкой сохранённого ответа через waitUntil с арендой и повтором через Cron при сбое. Проверено новым настоящим /start; D1 показал sent уже через 2 секунды после события. Для следующих проверок: Проверить повтор, просрочку, отзыв и архив. Проверить изоляцию двух мастеров в настоящем Telegram: записи, клиенты, заметки; администратор видит оба профиля. Автоматические проверки пройдены, живые ещё нет.
4. **Основной живой сценарий выполнен:** пользователь подтвердил статус номера; D1 содержит один использованный запрос и один подтверждённый контакт. Значение номера не выводилось. CONTACT_VERIFICATION_ENABLED включён с отдельного разрешения. Негативные варианты проверены автоматическими тестами; живые повтор/просрочка ещё не отмечать выполненными. Для следующих проверок: Пользователь сначала видит согласие на сохранение номера в Cloudflare и доступ уполномоченным сотрудникам. Приложение создаёт десятиминутный запрос, затем вызывает официальный requestContact. Номер подтверждает только защищённый личный webhook с совпадением from.id=chat.id=contact.user_id, свежей датой и без пересылки. JavaScript не может подтвердить номер. Проверить повтор/просрочку, затем зафиксировать результат без номера в журнале.
5. Создать/перенести/отменить вымышленный визит, проверить уведомления HY/RU и оба напоминания, конфликтующий слот и повторное нажатие. Реальные записи остаются выключены.
6. После проверки /start включить TELEGRAM_LINKS_ENABLED. Ссылки ?start=booking и ?start=barber_<id> выдают web_app-кнопку без Main Mini App в BotFather. Проверить QR камерой и выбор нужного мастера. После переименования бота обновить BOT_USERNAME, MINI_APP_URL (если задан), приглашения и QR.

После живых сценариев завершить проверку бесплатных лимитов/CPU, процедуры экспорта и удаления данных, хранения и поддержки, затем доработать дизайн. Коммерческий запуск требует отдельного разрешения. Перенос webhook не означает готовность продукта или включение реальных записей.
