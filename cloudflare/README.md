# 37 Barbershop — изолированная демоверсия Workers + D1

Неофициальная закрытая демонстрация. Реальные записи отключены на сервере. Проверка контакта включена для согласованного теста: только разрешённый пользователь после явного согласия Telegram может подтвердить собственный номер. Реальные визиты остаются выключены. Исходная версия FastAPI/Render сохранена. Webhook и меню @ArminaHair_Bot переключены на Cloudflare с явного разрешения пользователя. Render сохранён с отключённой авторегистрацией; [результат, возврат и живые проверки](TELEGRAM_MIGRATION.md).

## Локальный запуск

**Текущий бот — @Barber37Bot.** Переход разрешён пользователем и выполнен; ACTIVE_BOT=next выбирает NEXT-секреты, исходные ключи сохранены. Старый бот направляет в новый. [Текущий результат и возврат](BOT_REPLACEMENT.md). Ссылки на ArminaHair_Bot ниже описывают прежнюю миграцию/режим возврата.

Нужны Node 24 и pnpm 11. Устанавливать из этого каталога:

```sh
pnpm install --frozen-lockfile
pnpm check
pnpm test
pnpm db:local
pnpm seed:local
pnpm dev
```

Открыть http://127.0.0.1:8787. Каталог доступен для просмотра. Защищённые действия требуют действительной подписи Telegram и включения ID в DEMO_USER_IDS. Токены в проекте отсутствуют.

Для проверки Telegram заполнить **локальную** `.dev.vars` на основе `.dev.vars.example`; в облаке использовать Secrets. Отдельный тестовый бот удобен, но необязателен. Для проверки через @ArminaHair_Bot нужны только разрешённые тестировщики и отдельная кнопка новой версии в личном чате. Не менять его действующий webhook или публичное меню без отдельного разрешения. OWNER_IDS задаёт владельцев; DEMO_USER_IDS — разрешённых тестировщиков. Пользователь может одновременно быть владельцем и привязанным мастером. При блокировке/архивировании мастера его привязка Telegram очищается.

### Браузерная проверка без настоящего Telegram

BOT_TOKEN, OWNER_IDS и DEMO_USER_IDS не объявлены публичными vars в wrangler.jsonc: задавайте их как Cloudflare Secrets, чтобы deploy не перезаписывал закрытый список пустыми значениями. Вход владельца через текущего бота подтверждён пользователем. Webhook уже направлен на новый Worker; живые проверки /start, приглашений и доставки фиксировать отдельно.

```sh
node scripts/prepare-assets.mjs
pnpm exec wrangler d1 migrations apply barbershop-37-demo --local --config tests/wrangler.ui.jsonc --persist-to .wrangler/ui-proof
pnpm exec wrangler d1 execute barbershop-37-demo --local --config tests/wrangler.ui.jsonc --persist-to .wrangler/ui-proof --file seeds/demo.sql
pnpm exec wrangler dev --local --config tests/wrangler.ui.jsonc --persist-to .wrangler/ui-proof --port 8788
```

Это отдельный локальный тестовый entrypoint с вымышленным Telegram ID 1 и несуществующим токеном. Он генерирует подписанный тестовый контекст, а API проходит обычную HMAC-проверку. **Не разворачивать tests/wrangler.ui.jsonc в облаке.** Основная конфигурация использует только `src/index.ts`; тестовый bootstrap не попадает в её сборку. Браузерные тесты не доказывают доставку настоящих сообщений Telegram.

- Ограничение 1 будущей онлайн-записи для нового клиента / 2 после завершённого визита; ручные записи не используют этот лимит.
- Приватные заметки в контексте мастера и его клиента.
- Календарь владельца/мастера с периодом до 31 дня, фильтрами по мастеру/статусу, историей архивных профилей и курсорными страницами по 100 визитов. Права мастера ограничены сервером.
- Список клиентов владельца с пагинацией, историей завершений/неявок и блокировкой новых онлайн-записей. Изменение доступа проверяет прежнее состояние, пишет аудит и сохраняет существующие визиты.
- Отключение/архивирование с просмотром назначенных визитов, сохранением или явно подтверждённой отменой всех. Отдельная ревизия записей защищает от отмены непросмотренного визита при гонке с новым бронированием.
- Передача визита другому мастеру владельцем: прежние цена/название/длительность сохраняются, конфликт или неподходящая услуга откатывают действие. Клиент и оба связанных действующих мастера получают задания уведомлений.
- Локализованные HY/RU уведомления о создании/переносе/отмене и напоминания, замороженный снимок события, подавление устаревших заданий и запрет доставки сотруднику после отзыва доступа. Старые текстовые задания остаются совместимыми; значения секретов не входят в сообщения.
- Описания HY/RU и порядок услуг редактируются в кабинете владельца. Выбранный язык авторизованного пользователя восстанавливается с сервера.
- Диагностика доставки владельца: фильтр состояния/пагинация, понятные причины, ограниченная проверка отправки самому себе и явно подтверждённый повтор подходящих ошибок. Telegram ID и тексты сообщений из списка не выдаются. Устаревшие и отозванные задания не воскрешаются; проверки сохранены и для старой текстовой очереди.
- Таблица уведомлений, ограниченные повторные попытки, аренда задания при параллельном Cron, напоминания 24ч/2ч, обработка 403/429. Абсолютная однократная доставка при сетевой неопределённости не гарантируется.
- Армянский по умолчанию, переключение на русский, мобильное тёмное оформление и предупреждение о демо.

## Как защищены интервалы

Обычная проверка «свободно → вставить» не используется как гарантия целостности. SQLite-триггеры **внутри операции D1** проверяют полный полуоткрытый интервал `[starts_at, ends_at)`, график, отсутствие и лимит клиента. Пересекающиеся записи одного мастера или клиента отклоняются. Соседние интервалы разрешены.

Создание клиента, записи, уведомлений и аудита выполняется одной D1 batch. При конфликте откатывается весь batch. Цена копируется через INSERT SELECT из каталога; дальнейшие изменения каталога не переписывают историю. Идемпотентность — UNIQUE(created_by, idempotency_key) плюс хеш нормализованного запроса. Повтор с другим содержимым возвращает 409. Перенос сохраняет исходную длительность и защищён номером версии.

График заменяется одной batch с последующей проверкой всех будущих визитов. CHECK-ограничение в служебной таблице откатывает замену, если хотя бы один визит оказался вне графика. Параллельная вставка записи/изменение графика сериализуются самой D1.

## Проверенные бесплатные лимиты

Сверено 22 октября 2026 по официальной документации. Workers Free: 100 000 запросов/сутки и 10 мс CPU HTTP-запроса; 50 subrequests на вызов. D1 Free: 5 млн прочитанных и 100 000 записанных строк/сутки; 500 МБ на базу, 5 ГБ суммарно, 10 баз; Time Travel 7 дней. Индексы и триггеры тоже расходуют ресурсы. Cron обрабатывает максимум 5 доставок за тик. CPU/суточную нагрузку нужно измерить на развёрнутом экземпляре; локальные тесты не подтверждают укладывание в облачный CPU-бюджет.

Цель — нулевая обязательная стоимость в этих лимитах. Платные сервисы не подключались. Бесплатный тариф не означает SLA или гарантированную круглосуточную доступность.

Источники: [Workers limits](https://developers.cloudflare.com/workers/platform/limits/), [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/), [D1 limits](https://developers.cloudflare.com/d1/platform/limits/), [D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/), [Telegram initData](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app).

## Резервирование и восстановление

Time Travel не заменяет независимую резервную копию. Для локальной проверки:

```sh
pnpm exec wrangler d1 export barbershop-37-demo --local --output demo-backup.sql
```

В облаке использовать `--remote` только с проверенным именем исходной базы. Хранить экспорт вне GitHub с ограниченным доступом; он может содержать персональные данные. Для восстановления создать отдельную пустую тестовую D1, импортировать SQL, проверить `foreign_key_check`, `quick_check`, количество услуг/мастеров/визитов, затем сценарии записи и авторизации. D1 не поддержала `integrity_check` в этой локальной проверке; использован разрешённый `quick_check`. Не импортировать поверх рабочей базы. Согласовать переключение только после проверки. Успех локального round-trip не является проверкой восстановления удалённой D1/Time Travel.

## Осталось перед коммерческой демонстрацией

Исключения графика, календарь, перенос/увольнение, персональные QR и диагностическая очередь реализованы. Код проверки контакта принимает только собственный свежий contact из секретом защищённого webhook после запроса пользователя; клиентский JavaScript не может подтвердить телефон. Эта функция отключена до согласованного теста после перехода. Одноразовые приглашения и ссылки запуска подготовлены; живые сценарии требуют миграции webhook. Облачные SQL backup/restore непустой вымышленной истории и Time Travel уже проверены на отдельных D1. Не завершены сохранение исходной Render SQLite, фактическое отключение старой регистрации/переключение, живые приглашения/контакт/визиты/напоминания, полный security/load/CPU QA, все мобильные формы и армянский носителем, политика хранения/экспорта/удаления данных и финальный дизайн. Перед реальными клиентами требуются согласие владельца и юридическая проверка для Армении. `APP_MODE != demo` блокируется сервером и не включает эксплуатацию.

## Контакт, администрирование и запуск бота

Фактический переход подготовлен в `src/cutover.ts`, но выключен: TELEGRAM_CUTOVER_REQUEST не задан. Его может включить только оператор после отдельного подтверждения пользователя. Он требует точный RENDER_GUARD_COMMIT, проверяет публичный /migration-status старого сервера и выключенную авторегистрацию, затем сохраняет входящую очередь при замене webhook и проверяет webhook/кнопку меню. Одноразовый запрос не исполняется повторно, при неопределённом результате требуется проверка. Публичного/клиентского endpoint для переключения нет. Подробности и разрешения — в TELEGRAM_MIGRATION.md.

`ADMIN_IDS` — закрытый серверный список уполномоченных администраторов с теми же правами управления, что у OWNER_IDS; профиль мастера не требуется. Пользователь не может назначить себя администратором из Mini App или через /start. В закрытом демо администратор также должен входить в DEMO_USER_IDS. Никому новые права автоматически не предоставляются.

При включении `CONTACT_VERIFICATION_ENABLED=true` перед первой онлайн-записью требуется серверное подтверждение номера. `/api/me/contact-challenge` принимает пустое тело, создаёт десятиминутный запрос; официальный `requestContact` вызывается после понятного согласия. Только подписанное событие Bot API с личным чатом и совпадением from.id/chat.id/contact.user_id сохраняет номер. Пересылка, чужой контакт, старая дата, просрочка и повтор не подтверждают его. `/api/me/contact` выдаёт только boolean, не телефон. Ручные демозаписи не требуют контакта. Реальные визиты всё ещё отключены независимо от этого флага.

`APP_URL` — точный HTTPS origin кнопки запуска. При `TELEGRAM_LINKS_ENABLED=true` персональная ссылка использует /start barber_<id>, бот отвечает кнопкой web_app с выбором мастера. Это не требует настройки Main Mini App в BotFather. В ссылке нет прав доступа. Длинные payload безопасно остаются браузерными ссылками; прямой MINI_APP_URL поддерживается отдельно. Флаг включать после реального теста.

Фоновый `checkBotConnection` вызывает только getMe/getWebhookInfo и хранит ограниченное состояние в integration_status. Токен, секрет и текст ошибки Telegram не сохраняются. Владелец проверяет его из раздела уведомлений; обычному клиенту endpoint закрыт. `LEGACY_CALLBACK_FORWARDING_ENABLED` и `LEGACY_WEBHOOK_SECRET` нужны для сохранения старых кнопок модерации: адрес Render жёстко закреплён, произвольная пересылка клиентом невозможна. Без настройки обработчик возвращает 503, сохраняя возможность повтора Telegram, а не молча теряя событие. Ничего не вызывает setWebhook автоматически.

## Телефон, быстрые уведомления и экспорт

В карточках визита/клиента администратора и своего мастера показывается сохранённый телефон с возможностью позвонить. В новых уведомлениях назначенному мастеру используется подтверждённый номер; клиентская копия и уведомление прежнему мастеру при передаче визита его не раскрывают. Технический ID визита убран из текста уведомлений. Уже отправленные сообщения не редактируются.

Уведомления хранятся в очереди до отправки. Успешная мутация визита, /start и тест самому себе запускают ограниченную фоновую отправку через Worker waitUntil. Максимум два соответствующих задания на HTTP-событие, остальные и повтор после ошибки остаются Cron. Аренда и проверки версии/доступа общие для обоих путей. Массовое архивирование остаётся очередью Cron, без неограниченной рассылки из запроса.

«Управление → Экспорт данных»: 11 наборов бизнес-данных, части по 250 строк, явное продолжение и скачивание JSON. Доступ только администратору, включая ADMIN_IDS. Приватные файлы не передавать в GitHub. Выгрузка не является полной SQL-копией для восстановления; на время частей приостановить изменения. [Данные, запрос удаления и прекращение обслуживания](DATA_PRIVACY.md). Полное необратимое удаление/обезличивание и утверждённые сроки пока не реализованы; не выдавать этот регламент за готовую юридическую политику салона.


### Получение экспорта в Telegram

Обычная ссылка на Blob в некоторых Telegram WebView открывает JSON текстом. После подготовки части есть отдельная кнопка «Получить файл в чате»: подписанный администратор явно просит отправить серверный JSON-документ лично себе. Получатель берётся только из проверенной подписи, произвольные chat_id/содержимое запрещены. До 3 попыток в минуту на аккаунт; автоматического повтора нет. После сетевой ошибки сначала проверить чат, чтобы не создавать дубликат. Каждая часть до 250 строк; продолжение доступно после принятия документа Telegram. Это не подтверждение сохранения пользователем. Копия с личными данными выбранного раздела остаётся в Telegram, о чём интерфейс предупреждает перед нажатием. Удаление из D1 не удаляет сохранённые/отправленные копии. Для безопасного теста выбирать «Услуги и цены».
